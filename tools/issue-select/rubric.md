# Rubric: is this a good first issue?

## Checks

Measure recency against the bundle's capture date in eval mode and today's date in live mode. Read the full available thread, not only the title and labels. Apply live-mode house rules from scope.md; they do not apply to frozen eval bundles.

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Human maintenance | Repo-facts last five default-branch commits and maintainer first-response sample; dated OWNER/MEMBER/COLLABORATOR posts in the issue thread. In live mode inspect those same commit and issue histories. | At least one human-authored default-branch commit or bot merge of a human-authored PR within 90 days, OR a maintainer post on this issue within 90 days, OR at least two sampled issues with a maintainer first response within 30 days of opening. Automated dependency updates alone do not establish human maintenance. | required |
| Active project | Repo-facts archived flag, latest release date, and last push date; in live mode the repository banner, Releases, and branch activity. | The repository is not archived, and either a release is at most 365 days old or a push is at most 90 days old. A project without releases can pass via pushes. Stars alone cannot pass this check. | required |
| Bounded contribution | Issue body, full available comment thread, and linked-attempt history; maintainer statements about intended behavior, affected components, and implementation difficulty. | The request is one identifiable code, test, or documentation change with an observable outcome. Reject pure support questions, umbrella/tracking work spanning independent tasks, unresolved competing designs without a settled direction, explicit requirements to change core parser/compiler/architecture internals, or issues at least two years old with at least two closed unmerged attempts at the same change. A short description, absent reproduction steps, multiple related acceptance criteria, or missing good-first-issue label does not alone fail this check. | required |
| Available work | Issue state, assignees, linked PR states, and every available claim/PR comment; inspect PRs mentioned in comments as well as the Development sidebar in live mode. | The issue is open, has no assignee and no open implementation PR, and has no unreleased claim or offered implementation in the thread. A later explicit withdrawal or maintainer invitation supersedes an earlier claim; a closed unmerged PR alone does not reserve the issue. A reported implementation PR with unknown current state is unclear, not evidence that the issue is free. In Path Review live mode apply the classroom sharing exception stated in scope.md. | required |
| AI workflow permitted | Repo-facts contribution-policy statement; in live mode CONTRIBUTING files, linked contributor guidance, dedicated AI policies, and issue/PR template requirements. | No applicable policy bans the intended AI-assisted contribution workflow. Policies permitting assistance subject to disclosure, personal understanding, testing, or human review pass, with those conditions recorded. A ban on fully AI-generated work is not a ban on explicitly permitted assistance. Explicit silence or no restriction after checking the named sources passes; unavailable policy evidence is unclear. | required |
| Easy verification | Reproduction steps, expected/actual behavior, examples, test references, and maintainer guidance in the body and comments. | The report provides a concrete reproducer, a specific existing test to extend, or an explicit before/after example that can verify the change. | preferred |

## Verdict rule

Accept only if every required check passes. A required fail or unclear means reject; explain the missing evidence for unclear. Execute and report every check even after finding a failure. Preferred checks never change the verdict: use them to rank accepted issues, followed by the fit profile in live mode. A label, high star count, or good personal fit cannot override a required failure.
